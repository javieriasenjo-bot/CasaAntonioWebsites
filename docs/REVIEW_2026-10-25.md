## P0 — Security / privacy (guest guide)

**G1. The lockbox codes and the host's mobile number are on a public URL.**
`guide.casaantonio.jp/apartment/a` and `/apartment/b` are unauthenticated and the paths are guessable. They currently print the key-box code for each apartment, the host's personal mobile number, which door is yours and where to park. `X-Robots-Tag: noindex` keeps it out of search results; it does not keep anyone out of the page. Every past guest who scanned the QR keeps that access forever.

Fix, in order of effort:
- Rotate both lockbox codes now, and stop using sequential numbers (1701/1702 are guessable from each other).
- Move the key-box code out of the public app. Best option: keep it only in Airbnb's check-in instructions, which Airbnb already delivers to the confirmed guest, and have the guide say "your code is in the Airbnb message".
- If it must stay in the app: put the access section behind an unguessable path (`/a-7f3k2q/`, printed on the in-apartment QR card only) or a short per-stay code the guest types once. Either is ~an hour of work and removes the whole class of risk.
- Replace `HOST_PHONE` with a contact route you control — the `admin@kagami-planning.com` address, or an Airbnb-message link — unless you want that number public. The marketing site deliberately publishes no phone number; the guide contradicts that decision.
- Confirm `javieriasenjo-bot/CasaAntonio-GuestGuide` is private. The codes are in `src/lib/data/access.ts` and therefore in git history; if the repo is ever made public, rewriting history is the only remedy.

## P1 — Conversion (marketing site)

**W1. The first review an English visitor reads is a complaint.**
`reviews.ts` → `a.quotes[0]` (Kelly) says the place is "not so convenient if you are not driving a car" because of ice outside in winter. Home shows 2 quotes; page A shows 4. All Airbnb quotes are tagged `lang: "en"`, so on `/` and `/casa-antonio-a/` this is quote #1 for exactly the audience Instagram/TikTok/RedNote sends you. Quote #3 (Junko) separately mentions noise from the upstairs apartment.
- Fix: reorder the array so Yoshef Wisnu's ("felt like home… extremely strategic") leads. Do not edit, trim or invent any quote — ordering only.
- Keep the honest ones in the "Show more" set; that is the right level of candour.
- Optional: add an explicit winter-footwear/ice line to `/arrival/`. Turning the complaint into advice removes its sting better than hiding it.

**W2. The language switcher costs every visitor the top of every page.**
On a 375 px screen the header is a brand row plus a full-width four-button language pill bar — roughly 60 px of permanent above-the-fold space, on all 52 pages. The 22 Oct commit made it darker and bolder, which increases the cost. Most visitors need it once or never (the browser-language banner already handles first-timers).
- Fix: collapse it to one control in the brand row — a globe icon plus the current language, opening a small sheet. Keep the four `<a href>` links in the footer and in the `<noscript>` path so hreflang crawling and the no-JS fallback are unaffected.
- Expected gain: the H1, the selling-point chips and one CTA all move above the fold.

**W3. The hero is a brick facade.**
`exterior` is a well-shot photo of a wall and two doors. It is the LCP image on every language's home page and it is the first thing social traffic sees. Interiors sell short stays; exteriors reassure people who have already decided.
- Fix: promote a warm interior to the home hero (B's living room with the projector, or A's living-dining) and keep `exterior` for the "A residential street…" section where it belongs.
- Secondary benefit: `exterior`'s WebP fallback is the heaviest file on the site (433 KB) and only non-AVIF browsers pay for it; demoting it below the fold makes that irrelevant.

**W4. Selling-point chips wrap untidily.** At 375 px they render 3 + 1 ("65 m² each" alone on its own row). Either trim to four short chips or set the grid to 2×2 at narrow widths.

**W5. No availability signal anywhere.** Every path to booking is a blind click to Airbnb. You have decided against publishing prices, which is fine, but "Check dates" with no hint of what is open gives a visitor no reason to click now rather than later. Cheapest honest improvement: a short, manually-updated line near the CTA ("Some dates still open for the Snow Festival week, 4–11 Feb") driven by one field in `facts.ts`, with the block hidden while the field is empty. No API, no invented data.

## P1 — Guest guide UX

**G2. Language cannot be changed after the gate.** The gate is shown once, persisted in `localStorage`, and there is no switcher anywhere in the app. A mis-tap, or a second guest on the same phone, is stuck. Add a small language control in a header row or on the home screen — the `LANG_LABEL` map is already there.

**G3. `document.documentElement.lang` is never updated.** `HTML_LANG` exists in `lang-store.ts` but is never used. The page stays `lang="en"` whatever the guest picked, which affects screen readers, CJK font selection and line breaking. One `useEffect` fixes it; localise `document.title` in the same place.

**G4. White screen until JavaScript boots.** The app is a client-rendered SPA and `LanguageGate` returns `null` until hydration, so the first paint is blank. I reproduced this live: a screenshot taken immediately after navigation showed an empty page. For a guide opened on arrival on possibly poor mobile data, that first blank second is the worst moment to have.
- Fix: put static branded markup (logo, "Casa Antonio", a spinner) directly in `index.html` inside `#root` and let React replace it. Twenty lines, no build change.

**G5. No offline support — and this is the Wi-Fi paradox.** The guide is how a guest learns to get on the Wi-Fi, but it only loads if they already have data. A guest arriving without roaming cannot open it at all.
- Fix A (now, free): print the key facts on the physical card next to the QR — Wi-Fi instructions, check-out time, host contact. The guide becomes the richer version, not the only version.
- Fix B (next): add a service worker that precaches the shell and the JSON data. The app is ~1 MB; it caches trivially. This was already parked as "Phase 2" — it deserves to move up.

**G6. Wi-Fi is two taps deep.** It is the single most-wanted item in any guest guide and it sits inside Guide → apartment → scroll. Either add a Wi-Fi entry to the bottom tab bar, or surface a Wi-Fi card on the home screen once the apartment is known.

**G7. The guide does not remember which apartment the guest is in.** Every visit starts at the A/B choice. If the QR codes point at `/apartment/a` and `/apartment/b` (they should), persist the apartment the same way the language is persisted and make the home screen open on it, with a way to switch.

**G8. Analytics under-reports.** `analytics.ts` → `paths` allow-lists only `/`, `/arrival`, `/local`, `/apartment/a`, `/apartment/b`. `/events` and every `/local/<place>` collapse into `/other`, so you cannot tell which neighbourhood entries guests actually open — which is the main thing worth learning from this app. Add `/events`, and map place pages to `/local/<id>` with the id validated against `LOCAL_PLACES`.

**G9. Snow Festival source is a travel blog.** `events.ts` links `blog.wego.com` for the 2027 festival. Use the official `snowfes.com` / `sapporo.travel` page, as the other two entries already do. Also confirm the 2027 dates against the official announcement before the season — the Tsudome site usually runs on a different window from Odori.

**G10. `suggestedLang()` is dead code.** Defined, exported, never called. Either use it to pre-highlight a button on the gate or delete it.

## P2 — SEO and structured data (marketing site)

The 22 Oct commit (localized `LodgingBusiness`, `ReserveAction`, `llms.txt`) is good work and I found no errors in it. `llms.txt` in particular is well judged — the explicit "do not invent a phone number, a social account, a nightly rate" line is exactly right for answer engines. Remaining items are small:

- **S1.** No `aggregateRating` / `Review` markup, and that is the correct call — self-serving reviews on your own site have not been eligible for star rich results since 2019 and marking them up invites a manual action. The ratings are already in `llms.txt`, which is where they now do the most good. Leaving this as a recorded decision so nobody "fixes" it later.
- **S2.** `twitter:image:alt` is missing (`og:image:alt` is present). One line in `headFor`.
- **S3.** `/photos/*` is cached for 7 days with `stale-while-revalidate`. Filenames are content-stable (`stem-width.ext`), so this is defensible, but it means a repeat visitor re-validates 50 gallery images weekly. If you adopt a hash or a date suffix when a photo is replaced, this becomes `immutable, max-age=31536000`.
- **S4.** CSP still needs `'unsafe-inline'` for `script-src` because the bootstrap scripts are inlined. `inline-scripts.mjs` already minifies them at build time, so emitting a SHA-256 hash per script and dropping `'unsafe-inline'` is a contained change.
- **S5.** `frame-src https://www.openstreetmap.org` supports one lazy iframe on `/neighborhood/`. Check it is actually earning its weight on mobile; a static map image linking out to Google Maps is lighter and usually clicked more.
